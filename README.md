# Bagelbite

Bagelbite teaches programming topics in **bites**: short lessons interleaved with questions you answer
from memory, a real code exercise checked by tests, and an in-lesson AI tutor. Questions come back on a
spaced-repetition schedule (FSRS), and a bite only counts as **mastered** once you've recalled it correctly
in two separate sessions — mastery, not completion, unlocks what builds on it.

v1 is deliberately narrow: programming and tech topics, for learners who already have adjacent
knowledge ("I know JavaScript, new to React"). Curricula and lesson content are generated by Claude
once and **shared** by every learner of the same topic; personalization is a thin layer (scaffolding
tier, question selection, review scheduling).

> Product and design docs live in the Obsidian vault (`Projects/Bagelbite/`, final scope in
> `MVP-Synthesis.md` + `Content-Sharing.md`). How those docs were interpreted during the build is
> recorded in [`PROJECT_NOTES.md`](PROJECT_NOTES.md); the milestone plan is in [`PLAN.md`](PLAN.md).

## What's in v1

- Google sign-in (Firebase Auth)
- Topic entry + one-line background; broad topics (".NET", "web development") are narrowed via a
  short pick-list first; non-programming topics are declined
- Shared curriculum per topic (Claude Sonnet) with a risk tier per concept and related topics captured
  for the future topic graph
- Lessons generated lazily per concept and scaffolding tier, cached forever and reused by everyone:
  explanation sections interleaved with free-recall questions, plus a Sandpack JavaScript exercise whose
  test spec is validated in a sandbox before anyone sees it
- Content-accuracy floor: medium/high-risk concepts are grounded with a Tavily search first and cite
  sources; high-risk (security) content is independently verified, regenerated once, then hedged
- Grading: exercise tests run in the browser; free-recall answers are graded by Claude Haiku, with
  pre-written corrections for anticipated misconceptions
- Confidence rating (1–4) before every reveal, self-rating (Again/Hard/Good/Easy) after, `ts-fsrs`
  scheduling, mastery gate, a "what's next" composer that puts due reviews first
- Adaptive difficulty: a deterministic success-rate signal picks the scaffolding tier of the next bite
- In-lesson chat tutor (streamed, capped history), "report an issue" on every content block
- Instrumentation for the "is it working" queries: attempts, review logs, sessions, flags, mastery
  events, cache hit/miss, and token usage per Claude call

Deferred by design (see the vault's `MVP-Synthesis.md`): diagnostic pretest, the topic-graph screen,
interleaving, gamification, the community course bank, non-code exercise types, mobile.

## Getting started (no API keys needed)

Requires **Node.js 22.13+** (the exercise sandbox uses Node's permission model).

```bash
npm run install:all
```

```bash
cp backend/.env.example backend/.env
```

```bash
cp frontend/.env.example frontend/.env.development.local
```

Then run the API and the web app in two terminals:

```bash
npm run dev:api
```

```bash
npm run dev:web
```

Open http://localhost:5173 and use the **dev sign-in**. The example env files run fully offline:

| Setting | Local default | Effect |
|---|---|---|
| `DATABASE_URL` unset | embedded PGlite in `backend/.data/` | Real Postgres (WASM), no install |
| `AUTH_MODE=dev` / `VITE_AUTH_MODE=dev` | dev sign-in | No Firebase project needed |
| `LLM_PROVIDER=offline` | template content | Clearly labelled "offline demo content" — not real lessons |
| `GROUNDING=off` | no source search | Medium/high-risk bites are marked "not source-grounded" |

All four are refused at startup when `NODE_ENV=production`. The Sandpack exercise editor loads its
bundler from codesandbox.io, so exercises need an internet connection.

### Using the real services locally

In `backend/.env`: set `LLM_PROVIDER=anthropic` + `ANTHROPIC_API_KEY`, `GROUNDING=tavily` +
`TAVILY_API_KEY`, and optionally `DATABASE_URL`. For real sign-in set `AUTH_MODE=firebase` +
`FIREBASE_PROJECT_ID` (+ `FIREBASE_SERVICE_ACCOUNT_JSON`) and, in the frontend env, `VITE_AUTH_MODE=firebase`
plus the `VITE_FIREBASE_*` values from the Firebase console (enable the Google provider and add
`localhost` to authorized domains).

## Tests, lint and typecheck

```bash
npm test
```

```bash
npm run lint
```

```bash
npm run typecheck
```

- **Backend (Vitest + supertest):** every endpoint against a fresh in-memory PGlite per file, a scripted
  AI fake, and the real exercise sandbox. Covers topic scoping and shared-skeleton reuse, the lesson
  pipeline (grounding, verification/hedging, exercise validation and repair), grading and the
  misconception bank, FSRS scheduling and the two-session mastery gate (with a fake clock), the
  composer, attempts, flags, the SSE tutor, and the metrics SQL.
- **Frontend (Vitest + Testing Library):** UI primitives, the answer → confidence → reveal → rating
  flow, citations, flags, the disambiguation round-trip, the review session, SSE parsing.
- **CI** (`.github/workflows/ci.yml`) runs the same lint/typecheck/test/build for both apps on every PR.
  To make it block merges, require the `backend` and `frontend` checks in branch protection for `main`.

## Deploying

**API → Railway.** Create a service from this repo with **root directory `backend`**
(`backend/railway.json` sets the build/start commands and the `/health` check). Add the Postgres plugin
and reference its `DATABASE_URL`, then set `NODE_ENV=production`, `CORS_ORIGINS`, the Firebase,
Anthropic and Tavily variables. Migrations run automatically on startup.

**Web → Vercel.** Import the repo with **root directory `frontend`** (`frontend/vercel.json` handles the
SPA rewrite). Set `VITE_API_URL` to the Railway URL and the `VITE_FIREBASE_*` values, and add the Vercel
domain to Firebase's authorized domains.

## Operating it

- **Content flags** — "report an issue" creates a flag on shared content; high-risk content is hidden
  immediately and regenerated on the next view. Review the queue by hand:
  `npm run flags --prefix backend` lists open flags; `npm run flags --prefix backend -- confirm <id>`
  retires the content for everyone; `... -- dismiss <id>` closes it.
- **Metrics** — `backend/scripts/metrics.sql` holds the "is this working" queries (activation,
  retention proxy, mastery reach, drop-off, cost per learner, cache hit rate, calibration…):
  `psql "$DATABASE_URL" -f backend/scripts/metrics.sql`.
- **Schema changes** — edit `backend/src/db/schema.ts`, run `npm run db:generate --prefix backend`,
  commit the new file in `backend/drizzle/`.

## API

All routes except `/health` require `Authorization: Bearer <Firebase ID token>`. Types are in
[`shared/api.ts`](shared/api.ts).

| Method | Path | Purpose |
|---|---|---|
| POST | `/topics/enroll` | Enroll: `resolved`, `disambiguate` (candidates) or `unsupported` |
| GET | `/users/me/enrollments`, `/users/me/dashboard` | Topic cards, mastery-weighted progress, due counts |
| GET | `/topics/:topicId/enrollment` | Curriculum with per-bite status |
| GET | `/topics/:topicId/next` | What to do next (reviews / bite / waiting / completed) |
| GET | `/bites/:id` | Compose a bite (generates shared content on first ever view) |
| POST | `/bites/:id/retrieval-prompts/:promptId/response` | Grade an answer (+ confidence) |
| POST | `/review-logs/:id/rating` | Self-rate recall → FSRS schedule → mastery check |
| GET | `/users/me/reviews/due` | Due review questions across topics |
| POST | `/bites/:id/attempts`, `/bites/:id/reveal-solution` | Exercise attempts; solution after 3 failures |
| POST | `/bites/:id/flag` | Report an issue with a lesson, question or exercise |
| GET/POST | `/bites/:id/chat` | Tutor history / streamed reply (SSE) |
